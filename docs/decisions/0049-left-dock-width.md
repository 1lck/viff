# 0049 左侧工具窗共用一个宽度

- 状态：已采用（2026-11）

## 背景

Project 树与 Commit 面板共用左侧停靠区，一次只显示一个，但两者此前各存一个宽度：`projectPanelWidth`（默认 300）与 `commitPanelWidth`（默认 340），clamp 上限也不相同。用户在两个页签间切换时分隔线会横移，右侧编辑器宽度跟着变化；在 Project 里拖动分隔条也不会影响 Commit。Issue [#87](https://github.com/1lck/viff/issues/87) 报告了这个可见抖动：同一个停靠区不应因为换了页签就变成另一种宽度。

宽度是用户可见的布局状态，又写在 `settings.json` 里，所以修复不能只改绘制代码：旧文件里的两个键必须迁移，且升级后不能突然变窄。设置格式的选择属于需要留下理由的长期维护成本。

## 替代项

- **保留两个字段，切换页签时套用各自宽度。** 保留历史宽度，但切换仍会横移分隔线，正是 issue 要修的现象，不采用。
- **保留两个字段，但每次拖动都同步写另一个。** 内存和磁盘上仍有两个权威值，读只读设置、旧文件迁移和写入失败时都可能让两者分叉；多出来的同步逻辑没有换来用户可见的好处，不采用。
- **统一字段但不迁移旧值，直接使用新默认。** 用户调过的宽度会丢失，升级后面板宽度突变，不采用。
- **统一字段，迁移时取较窄的 `projectPanelWidth`。** 升级后 Commit 面板会从默认 340 突然缩到 300，与「升级不改变看到的内容」冲突；Project 面板本来就是较窄的一页，变宽 40px 比让正在用的 Commit 面板变窄更容易接受，不采用。
- **递增 `SchemaVersion` 以标记新格式。** 新字段对 0.4.5 是未知键，旧版本会忽略它；一旦递增版本号，旧版本会把文件判为「更新版本」而只读，反而扩大不兼容面。迁移是幂等的字段折叠，不需要版本号区分，不采用。

## 决定

- `Settings` 只保留一个 `leftPanelWidth`（默认 340）。Project 与 Commit 读取同一个值，使用同一套 clamp（最小 240，最大为停靠区宽度减 300，给编辑器留出空间），两个页签的分隔条都写回这个字段。切换页签不改变分隔线位置；拖动任一侧后另一侧立即一致。默认取原 Commit 宽度，使正在使用 Commit 面板的用户升级后不觉得变窄。
- `Load` 把旧键折叠进规范字段：合法的 `leftPanelWidth` 按原样使用（本版本或更新版本写出的文件）；两个按页键都存在时，先看哪个值与旧默认不同——旧版本每次保存都会写出两个键，只有被拖动过的那一页会偏离默认，采用它就能保留用户实际调过的宽度；两者都调过或都没调过时取 `commitPanelWidth`（旧默认更宽，升级不突然变窄）；只有一个可用键时用它；都没有或非法时用默认 340。缺失或非法的键不会覆盖可用的键，因此当前键损坏时仍能回退到旧宽度。
- 旧键只作为迁移输入：它们不在 `Settings` 结构里，保存时不会再写出，磁盘上只留下 `leftPanelWidth`。这样内存和持久化都只有一个权威值，代码路径也无法再读到按页宽度。
- `sanitize` 对小于 200 的宽度回退默认；`Defaults` 同步为 340。`Load` 仍先采用旧键再 sanitize，迁移不会丢失合法值。

## 代价

- 两个页面不能再各自记住宽度。用户若希望 Project 更宽、Commit 更窄，只能每次切换后拖动，或者接受同一个宽度；这是 issue 要求的行为。
- 在无法判断用户调过哪一页时迁移取 Commit 宽度，因此新默认下 Project 面板比旧版宽 40px（300→340）。这避免了 Commit 面板变窄，但确实是可见变化。
- 旧键读一次后即被取代：下一次保存后 `settings.json` 里只剩 `leftPanelWidth`。设置格式版本没有递增，`Load` 不会为这次迁移写 `.v1.bak` 备份，需要保留旧值的用户应在升级前自行复制设置文件。降级到 0.4.5 时，旧版本不认 `leftPanelWidth`，会退回它自己的默认宽度（Project 300 / Commit 340），看不到迁移后的值。
- 迁移只看键值，不看用户当时在哪个页面拖动。如果用户同时调过两个宽度，只有一个值能保留：迁移取 Commit 宽度，Project 的调整会丢失；单值格式下无法同时满足两个不同的宽度。
- 未来若某个页面需要独立宽度，得重新引入按页键并再做一次迁移，届时需要递增 `SchemaVersion` 或设计能表达「共享基准 + 页面覆盖」的格式。

## 复审条件

- 用户要求 Project 与 Commit 各自记住不同宽度时，重新评估本决策，先设计共享基准与页面覆盖的字段格式，再决定是否递增 `SchemaVersion`。
- 设置页、诊断包或文档需要展示布局字段时，确认只显示 `leftPanelWidth`，不要重新引入按页键作为第二权威值。
- 旧版本回退成为必须支持的能力时，写入 `leftPanelWidth` 的同时写出旧键会重新引入双权威值；必须先把旧键限定为只读的降级副本，并说明冲突时以哪个键为准。
