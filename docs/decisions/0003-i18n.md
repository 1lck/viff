# 0003 界面语言与消息表

- 状态：已采用（2026-11，阶段 0 落地；后续阶段按模块迁移）

## 背景
界面文案全部以英文字面量写在渲染处。要支持中文，最省事的是逐处替换成查表，但那样每个函数都要知道语言从哪来；反过来，如果先建一套重型本地化框架（外部资源文件、运行期解析、代码生成），又会把大量时间花在工具链上，而文案总量只有千余条。

## 决定

- **语言**：`en` 与 `zh-CN`，默认英文。设置里 `language` 为空即英文，因此旧设置文件的行为与之前完全一致。
- **资源形态**：消息表写在 Go 源码里，而不是 JSON/TOML 外部文件。理由：编译期即可发现 key 缺失与重复，不引入运行期解析失败和文件路径问题；校对时用导出清单即可，不需要为此引入代码生成。
- **分文件注册**：每个模块有自己的 `messages_*.go`，在 `init` 里注册自己的 `map[Key]string`。多个文件因此可以各自追加 key，既不共享一个字面量，也不会互相冲突——这也是并行迁移多个模块的前提。
- **Key**：点分命名空间的常量（`settings.group.fonts`、`diff.notice.binaryAdded`），拼写错误编译失败，不会把 key 显示到界面上。
- **入口**：`Window.t(key, args...)`。缺失条目回退英文，再回退 key 本身，界面不会出现空白。
- **分层边界**：
  - `ui` 直接翻译；
  - `app` 的通知与用户可见错误按“键 + 参数”返回，由 `ui` 渲染，避免业务层依赖表现层；
  - `domain` / `gitcli` 不翻译，它们返回技术错误，只有少数需要用户阅读，由 `ui` 按错误类型映射。
- **不翻译**：Git 命令与输出、文件路径与哈希、快捷键组合、日志字段、诊断导出中的机器可读键。
- **测试**：测试夹具固定英文（默认语言），因此既有文本断言无需改动；另加一条“切到 zh-CN 后标题、页签与区块标题为中文”的回归用例。若今后把默认语言改成跟随系统，测试必须显式固定语言，否则 CI 会随宿主语言漂移。

## 阶段
0 框架 + 设置对话框；1 菜单、工具栏与 tooltip；2 主窗口面板与列表；3 diff、冲突与编辑器提示；4 应用层通知；5 诊断、关于与更新。每阶段独立提交，可单独回退。

## 代价
- 中文比英文宽约 1.5–2 倍：固定宽度（表单标签 170、树 220、按钮最小宽）需要按语言回归，必要时引入宽度常量而不是逐处硬编码。
- 每加一条文案要同时维护两种语言；缺失时虽然回退英文，但用户会看到夹生界面，需要靠复查清单兜住。
- 术语一致性靠人工维护（diff、commit、branch、stash 等译法见 `docs/features.zh-CN.md`）。

## 复审条件
支持第三种语言，或消息条目数超过约 2000 条、需要外部翻译工具协作时，改为外部资源文件 + 校验与导出工具；在此之前，源码表更省心。
