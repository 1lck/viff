# 0030 会话内全局撤销

- 状态：已采用（2026-11）

## 背景

Viff 的写操作都有确认或撤销入口，但彼此不通：提交后想收回要打开 Log 右键「Undo Commit」，误删分支要靠通知里的「恢复」，合并、变基、cherry-pick、reset、checkout 一旦做完只剩 reflog 可查。用户在一次清理动作里连做几步后，没有一条统一的「退回上一步」，而这正是 IntelliJ 等桌面 Git 客户端最基本的肌肉记忆（⌘Z）。

难点不在执行反向命令，而在**不能覆盖外部修改**。Git 是事实来源：外部 AI、hooks、其他终端都可能在本应用记录之后改 HEAD、分支或工作区。任何「按上次看到的状态硬重置」的实现都会把这些改动当作自己的撤销对象，造成数据丢失。

0.2 的第 2 项要求：会话内的全局撤销，覆盖后果大的本地操作，且撤销前必须重新校验。

## 替代项

- **用 reflog 做通用撤销**：一条 `git reset --hard HEAD@{n}` 看起来能覆盖所有操作，但 reflog 不区分本应用与其他终端、不记录分支删除/重命名、不记录「操作前工作区是否干净」，也无法拒绝外部改动；静默地按时间回退比不做更危险。
- **持久化撤销栈到设置**：跨重启的撤销听起来方便，但重启后 HEAD、index、分支都可能已被别人改动，记录的 after 状态几乎必然过期；持久化还会把仓库路径、分支名写进设置，扩大隐私面并需要迁移。会话内栈已经覆盖「刚做错、马上退回」的真实场景。
- **每条命令自己实现反向命令**：调用点分散、语义不一致，且绕不开「命令成功后才知道 after 状态」的问题；统一的 Run 钩子只写一次记录逻辑。
- **提交也只做 `reset --hard`**：实现最简单，但会丢掉提交后用户又暂存的工作；`reset --soft` 保留 index 与工作区，正好对应「把这次提交收回去、内容还在」的预期。
- **撤销前弹确认框**：多一次点击，且确认框无法表达「为什么这次不能撤销」；改为执行时重新校验，拒绝时用通知说明具体原因。
- **用 `sh -c` 拼 reflog 参数**：违反本仓库「参数数组、不经 shell」的硬约束，也处理不了分支名中的特殊字符。

## 决定

- **记录点统一在 `Workspace.run`**（`Run` 的私有带撤销版本）。命令仍通过写锁串行执行；进入锁后、执行命令前读一次 HEAD 状态（`git symbolic-ref --quiet --short HEAD` + `git rev-parse --verify --quiet HEAD`，机器输出，不扫描工作区），成功后、释放锁前再读一次。这样 before/after 是 Git 当时真实的状态，而不是界面缓存的旧快照；失败、取消、无法读取前后状态时都不记录。
- 记录内容：`kind`、仓库根、`beforeHead/afterHead`、`beforeBranch/afterBranch`（分离 HEAD 时分支为空）、操作涉及的引用名与 sha（删除分支记录被删的 sha，创建分支记录创建后的 sha，重命名记录新旧名与 sha，覆盖创建记录被覆盖前的 sha）、时间。超过 20 条丢弃最旧的一条；切换/关闭/移除仓库时清空。
- **覆盖范围**：commit、amend、merge、rebase（含交互式变基）、cherry-pick、revert、reset、checkout（分支与分离修订）、分支创建（含检出与覆盖）、删除、重命名。其余操作（tag、remote、stash、worktree、submodule、patch、hooks 相关）不改变 HEAD/分支集合或没有可靠的反向语义，不进入撤销栈。
- **撤销前校验**（全部在写锁内、用刚查到的 Git 状态判断）：
  1. 仓库根仍是记录里的仓库；
  2. 没有进行中的 merge/rebase/cherry-pick/revert/am/bisect；
  3. 当前 `HeadState`（HEAD 提交 + 分支名/分离状态）等于记录的 after；
  4. 需要改写工作区的种类要求工作区完全干净（含未跟踪文件），因为 `reset --hard` 可能覆盖目标提交里的同名未跟踪文件；
  5. 分支类操作再校验引用：创建/重命名要求分支仍指向记录的 sha，删除要求同名分支不存在，重命名还要求旧名未被占用，覆盖创建要求分支仍指向覆盖后的 sha。
  任何一条不满足都拒绝，用通知说明原因（操作进行中、HEAD 已变化、工作区不干净、分支已变化、分支又存在），记录保留，用户处理后可以重试。
- **撤销方式按操作语义区分**：

  | 记录的操作 | 撤销命令 | 理由 |
  | --- | --- | --- |
  | commit / amend | `reset --soft beforeHead` | 只移动 HEAD，index 与工作区不动：提交内容回到已暂存，工作区里后续的修改也不会被覆盖；因此这条路径允许脏工作区 |
  | merge / rebase / cherry-pick / revert / reset | `reset --hard beforeHead` | 这些操作都要求操作前工作区干净，成功后工作区干净；硬重置恢复的正是记录状态。撤销前再次要求干净，避免吞掉记录之后的新修改 |
  | checkout | 切回 `beforeBranch`，原先分离则 `switch --detach beforeHead` | 与记录的分支/提交状态一一对应；要求干净，避免切换时搬运或覆盖本地修改 |
  | 删除分支 | 按记录的 sha 重建同名分支 | sha 在删除前于锁内重新解析，外部在两次刷新之间的新提交也能恢复 |
  | 创建分支 | 仍指向记录 sha 时删除；若创建时覆盖了旧分支，则把旧 sha 写回；创建时切换过去则先切回原分支 | 撤销不得删除后来被别人提交过的分支；覆盖创建必须还原旧位置而不是一删了之 |
  | 重命名分支 | `branch -m 新名 旧名` | 先确认新名（或当前分支）仍指向记录的 sha，且旧名未被占用 |
- **撤销本身是普通写任务**：`Undo` 走 `Workspace.run`（不传撤销 spec），因此同样取写锁、显示任务、结束后 `Refresh(true)`；它不会被记录成新的撤销，连按 ⌘Z 会沿栈继续向前退。
- **界面**：⌘Z / Ctrl+Z（`keys.go` 的 `shortcut`）。焦点在文本编辑器时**不拦截**，把 ⌘Z 留给文本自身的撤销（否则在提交信息里按 ⌘Z 会去重置仓库）；项目菜单新增「Undo <操作名>」项（无记录时禁用），成功/拒绝都走既有通知。
- **不持久化**：撤销栈只活在当前 `Workspace` 内存里，不写设置、不写仓库元数据。

## 代价

- 会话内、单仓库、20 条：重启后不能撤销；切仓库即清空；多次操作后只有最近 20 步可退。
- 首次提交没有可回退的提交，不入栈（`beforeHead` 为空的命令一律不记录）。因此「撤销第一次提交」需要用户自己 `git update-ref -d` 或重置分支，界面不提供。
- `reset --soft` / `reset --mixed` 的撤销在「工作区必须干净」的校验下会被拒绝：它们自身会留下 staged/unstaged 差异，Viff 无法区分这是 reset 的产物还是用户的新修改；目前只保证 `reset --hard` 的撤销。
- 冲突后 `--continue`（merge/rebase/cherry-pick/revert）不会补记录：带冲突的写操作失败即不记录，继续后的结果不在撤销栈里。需要退回时仍走操作栏的 abort 或 reflog。
- 交互式历史编辑里的 reword/squash/drop 以及 pull、apply mailbox 不记录，保持本次范围之外；它们完成后栈顶记录的 after 不再匹配，⌘Z 会明确拒绝而不是误退。
- 分支覆盖的还原只恢复引用位置，不恢复 reflog 语义；被覆盖期间若有其他工具引用了旧 sha，仍要靠对象是否可达判断。
- 每条可撤销命令多出两次 `symbolic-ref` + `rev-parse`，撤销时多一次 `status`（仅需要干净校验的种类）。这些是本地进程调用，未做大仓库基准。
- 分支创建/重命名在写锁内额外解析一次引用；删除分支先解析再删除，多一次进程调用。
- 检出远端分支时 Git 会顺带创建同名的本地跟踪分支；撤销只切回原来的分支/提交，不删除这条新分支，因为创建它与切换是同一条命令，撤销不替用户决定是否保留。
- 撤销成功只弹通知，不提供 redo；重复撤销依赖栈的顺序，而不是 Git 的重做栈。

## 复审条件

- 需要跨重启撤销、redo、或按仓库保留更久的历史时，重做持久化格式与失效策略，并先解决「重启后 after 状态已过期」的校验问题。
- 需要把 reword/squash/drop、pull、`--continue` 纳入撤销时，为每类补反向语义与测试，而不是复用 `undoRebase` 的硬重置猜测。
- 撤销前校验把未跟踪文件也算作不干净；如果真实使用中这挡住了合法的合并/变基撤销，重新评估「干净」的口径，并证明 `reset --hard` 不会覆盖目标提交中的未跟踪文件。
- 大仓库上每次写操作多两次身份查询、撤销多一次 `status` 造成可感知延迟时，改为复用写任务结束后的刷新结果或引入更窄的 HEAD 查询。
- 需要撤销远程操作（push、远程分支删除）时单独决策：它涉及远端事实与他人可见历史，不应与会话内本地撤销共用一套记录。
