# 0017 浏览某个提交的仓库树

- 状态：已采用（2026-11）

## 背景
文件查看器能只读打开某个提交里的单个文件，但用户无法先看到该提交里有哪些文件。IntelliJ 的 “Show Repository at Revision” 正是这个入口：从 Log 选中提交，浏览它对应的整棵树。此前只能去终端跑 `git ls-tree`，或者把仓库 checkout 到那个提交。

## 决定
- 树来自一次 `git ls-tree -r -z --full-tree -l <rev>`，不读工作树也不读索引：浏览的是提交本身，与当前 checkout 无关。`-l` 顺带给出 blob 大小，省掉每个文件一次 `cat-file -s`；`-z` 让含空格、制表符、换行或非 ASCII 字节的路径原样返回（不带 `-z` 时 Git 会给路径加引号并转义）。
- 解析只依赖 Git 的输出契约：`<mode> <type> <sha> <size>\t<path>`，记录之间只有 NUL。大小字段为 `-` 时记为 -1（子模块指向 commit，没有 blob 大小）。模式原样保留，界面据此区分普通文件、可执行位、符号链接和子模块；结果按路径排序。
- 提交头（短哈希、作者、标题）直接用 Log 里已有的 `domain.Commit`，不再查询一次；只有树走后台命令（`Workspace.RevisionTree`），与其它查询一样在 `w.post` 里回到界面线程。
- 列表只绘制可见行：仓库可能有几十万个文件，过滤只重建索引切片，全量条目保留在内存里；滚动与键盘上下移动共用同一个 scroller，行 ID 按可见位置注册，所以不可见的行不会进入命中测试树。
- 打开沿用现有文件查看器（`DiffSource{Commit, Path, View: true}`），因此只读、blame、二进制与超大文件提示都与 “Open Repository Version” 一致，不维护第二套渲染。

## 代价
- 整棵树一次性读进内存；百万文件级别的仓库占用可观，但 `ls-tree -r` 本来就是全量输出，分页读取并不会更省。
- 子模块只能看到 gitlink，展开其内部树需要另一次命令。
- 过滤是大小写不敏感的子串匹配，不是 IntelliJ 的通配符语法。

## 复审条件
需要按目录折叠、在树里直接看某个文件的 diff，或过滤要支持通配符与路径段时，再扩展这次的决定。
