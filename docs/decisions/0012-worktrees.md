# 0012 工作树界面

- 状态：已采用（2026-11）

## 背景
Git 命令层早就支持 `git worktree add/remove/list`，但界面里没有任何入口，用户只能用命令行。更常见的问题是：某个分支已经在另一个工作树里检出，分支弹窗里点“检出”只会得到 Git 的报错，看不出原因。IntelliJ 的 Git 工具窗口用一个 Worktrees 面板列出所有工作树，并允许新建、删除、切换，Viff 缺的正是这一层。

## 决定
- 工作树列表放进仓库状态（`RepoState.Worktrees`），随状态、引用一起在后台刷新时读取一次 `git worktree list --porcelain`；分支弹窗和对话框都读同一份数据，不各自调用 Git。
- 入口只有一个：分支弹窗底部的“Worktrees…”。对话框列出每个工作树的分支（或 detached / bare）、短 HEAD 和路径，当前工作树排在最前并标记“current”。
- 行内动作放到对话框底部的按钮行（打开、删除、复制路径），不用右键菜单：对话框的焦点陷阱会挡住弹层，菜单点不到。双击一行等同于“打开”。
- 删除走单独的确认框，说明“分支和提交保留，未提交的改动丢失”，并提供强制删除开关；当前工作树不可删除。
- “New Worktree…”只创建新分支并检出到新目录：填分支名、路径、起点，路径按 `<仓库父目录>/<仓库名>-<分支名>` 自动建议，用户改过之后就不再覆盖。
- 在分支弹窗里，已被别处检出的本地分支在提示里标出所在目录，并把“检出”改成打开那个工作树。Git 自身的 `checkout` 行为不变，CLI 和工作区命令仍会如实报错。

## 代价
- 每次仓库刷新多一次 `git worktree list`，仓库多、磁盘忙时略增开销；`WorktreesLoaded` 之前对话框会先补读一次。
- 还不能把已有分支检出到新工作树，只能新建分支；“New Worktree”与 IntelliJ 的完整能力有差距。
- 工作树路径在窄对话框里靠左截断显示，完整路径要复制或打开后才看得到。
- 对话框内不能开右键菜单，这是当前弹层与焦点陷阱的限制，不是工作树特有的取舍。

## 复审条件
需要把已有分支检出到新工作树，或需要在对话框里加更多行内动作时，先让弹层能在对话框的焦点陷阱内获得焦点，再补菜单；如果刷新耗时明显，改为只在打开对话框和增删工作树后读取列表。
