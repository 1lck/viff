# 0051 可编辑的冲突结果栏

- 状态：已采用（2026-11；issue #89 第一阶段，Base 栏与批量非冲突应用不在本阶段）

## 背景

[0005](0005-read-only-conflicts.md) 把冲突查看器定为只读三栏，逐块接受只写入磁盘后整页重载；[0042](0042-in-app-editing.md) 的应用内编辑明确把冲突排除在外。issue #89 要求在一个界面里完成“对照双方 → 逐块选择 → 手动调整 → 保存并确认解决”，复杂冲突往往需要把两侧内容拼起来再改，只读对照加整块接受不够用。

现有实现已经有可复用的基础：Viva 的 `text.Editor` 负责输入、输入法、选区、剪贴板与撤销；`internal/ui/fileedit.go` 已经解决显示行、制表符/宽字符的点击定位、输入法窗口位置、语法着色和带陈旧检测的保存；`app.SaveFile` 会重读文件、比对 SHA-256 并原子替换，恢复行尾、BOM、末尾换行与权限位。本阶段要做的不是再写一个编辑器，而是把同一套缓冲区和写盘路径接到冲突页签的中间栏。

## 替代项

- **保持只读，继续逐块写盘**：现有路径能在接受后立刻看到磁盘结果，但任何手改都必须先落到磁盘或外部编辑器；接受会整页重载，撤销无从谈起，用户还要在“接受”和“手改”之间反复切换工具。否决。
- **先保存再接受**：每次逐块接受都先写盘，语义简单，但会在用户只想试一下某一侧时产生多次写入和多个陈旧检查点，撤销也只能退回上一个磁盘版本；手改后接受还要先解决“保存失败怎么办”。否决。
- **重写一个冲突专用编辑器**：输入、输入法、撤销、光标与几何映射都要再来一遍，还会和文件编辑器产生两套行为。否决；本实现把缓冲区抽成 `textBuffer`，两个界面共用。
- **本阶段顺带做 Base 栏、一键应用非冲突改动或四栏布局**：Base 需要新的三方布局与滚动同步，一键应用需要定义“非冲突”的判定与冲突块之外的写入范围，四栏会改变现有三栏的阅读习惯。都超出“可编辑结果栏”的核心闭环，留到后续阶段。否决。

## 决定

- **中间 Result 栏就地编辑**：冲突页签加载出可信的文本冲突后，中间栏直接绑定 `text.Editor`；左右两栏继续只读。输入、选区、光标移动、输入法、剪贴板、撤销/重做复用 Viva 原生文本服务；绘制、命中测试、几何与输入法窗口位置复用 `fileedit.go` 抽出的 `textBuffer`，不新增第二套编辑器。页签标题的未保存标记、关闭确认等守卫按同一缓冲区判断。
- **缓冲区是编辑期间的唯一事实来源**：行号、冲突块高亮、上一处/下一处导航、逐块接受和 Copy for AI 都从缓冲区重新解析的标记读取，而不是继续使用加载时的那份。手改导致标记不可解析时，接受与 Copy 先禁用；保存也会拒绝，避免写出连查看器都无法解析的标记集。
- **逐块接受改缓冲区，不写盘**：Accept Ours/Theirs/Both 用 `domain.ResolveConflictText` 生成新文本，再以“全选 + 插入”写回同一个编辑器，因此是一次可撤销的编辑；块外的顺序与手改保持不变，接受后光标回到被接受块的位置。磁盘只在 Save 时变化。选择这个方向而不是“先保存再接受”，是因为它保留未保存的手改、把多次尝试压成一条撤销历史，并让所有写入只经过一个陈旧检查点。
- **保存复用 `app.SaveFile`**：⌘S 或横幅的 `Save Merge Result` 调 `Workspace.SaveFile`，带上缓冲区打开时的 SHA-256；应用层重读文件，内容已变就返回 `ErrEditChanged`，缓冲区保持原样并弹出带 `Reload` 的警告。写入保留打开时检测到的行尾、UTF-8 BOM、末尾换行与权限位。保存成功后重载页签，标记数、两侧内容与 `Mark as Resolved` 的可用性都回到磁盘事实。
- **Mark as Resolved 仍是显式动作**：有未保存修改时按钮禁用（悬停说明先保存），磁盘上仍有标记时也禁用；只有保存成功且文件中没有标记，按钮才可用，之后沿用现有 `StagePaths` 与 Continue/Abort 流程，不自动提交。
- **未保存保护覆盖所有退出路径**：关闭页签、关闭其他/全部页签、关闭窗口、从菜单退出、切换或移除仓库、替换预览页签前，都会通过统一的 `dirtyBuffer` 询问是否放弃；取消则保留缓冲区与光标。切换页签本身不丢弃缓冲区。
- **外部改动不覆盖**：缓冲区干净时，状态刷新仍会按磁盘重新加载并重建缓冲区；缓冲区有未保存文本时不再自动重载，保存时的陈旧检查是唯一写入口，失败后保留文本并说明原因。通知里的 `Reload` 是显式放弃缓冲区的动作，不再二次询问。
- **只读回退不变**：远端仓库、只读仓库、Subversion（没有 `ConflictResolver` 能力）、二进制、超大（超过 1 MiB 编辑上限）、子模块、符号链接、非 UTF-8 和标记不可解析的冲突仍不可编辑；这些页签不显示保存/接受按钮，继续走外部编辑器或 `svn resolve`。
- **不做**：Base 共同祖先对照栏、一键应用非冲突改动（工作树文件本身已含 Git 自动合并的非冲突内容）、四栏布局。issue #89 合并后保持 open，后续阶段再评估。
- **旧接口保留**：`app.ResolveConflict` 与 `gitcli.ResolveConflictBlock` 不再被界面调用，但仍作为后端 `ConflictResolver` 能力存在；本阶段不改后端契约，是否删除在后续改动中单独决定（见复审条件）。

## 代价

- 保存成功会重载视图并重建缓冲区，撤销历史与光标位置随之清空；这是“保存后看到的必须是磁盘内容”的直接代价。保存期间继续输入的文本会保留为新的未保存修改，不会随重载丢失。
- 每个打开的冲突页签常驻一份文本、显示行与语法 span；上限与文件编辑器相同（1 MiB），更大的冲突仍只能用外部编辑器。
- 冲突块解析依赖标记完整。手改时误删一个标记会让接受、Copy 和保存同时拒绝，用户必须先补齐或删干净标记；代码里本来就有以 `>>>>>>>` 开头的行也会让解析不可靠。
- 只有保存时才会发现外部修改；缓冲区干净时的自动重载能覆盖大部分场景，但有未保存文本时会刻意不刷新，直到用户保存或显式 Reload。
- 中间栏没有 Base 对照，复杂冲突仍要凭两侧内容判断共同祖先；逐块接受按当前缓冲区的块序号工作，手改删掉前面的块后序号会变化。
- 左右两栏只读且不参与选择复制；结果栏的选区、复制与撤销行为与文件编辑器一致，但两者不共享撤销历史。
- Copy for AI 现在读取结果栏的当前文本，但行尾/末行换行等元数据仍来自磁盘文件；这对外部工具是提示，不是可执行契约。

## 复审条件

- 用户在复杂冲突里反复需要共同祖先：先做 Base 栏与三方同步滚动，再评估是否把“接受”扩展为三方选择。
- 用户反馈逐块接受后仍要手动复制 Git 已自动合并的非冲突内容：定义“块外差异”的判定与写入范围后另立决策，不把整文件覆盖当成默认。
- 出现“保存被标记解析拒绝，但用户确实只想保留这段文本”的反复反馈：评估允许保存并在重载后降级为只读，或提供“强制保存”并明确后果。
- 结果栏的撤销历史在保存后清空造成明显困扰：评估保存后保留历史（需要把 `original`/`expected` 与历史一起迁移），并补相应测试。
- Windows/Linux 实机的输入法、剪贴板或原子重命名在结果栏上发现问题：按平台能力回退为只读并回写本节。
- 后续阶段确认 `app.ResolveConflict`/`gitcli.ResolveConflictBlock` 不再需要：在单独改动中删除后端契约、测试与 i18n 文案，避免长期保留无调用方的写路径。
