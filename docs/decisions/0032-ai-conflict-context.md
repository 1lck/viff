# 0032 冲突上下文复制给外部 AI

- 状态：已采用（2026-11；只写剪贴板，不新增网络出口与模型调用）

## 背景

冲突查看器已经能展示 ours/base/theirs、按块接受某一侧，并在文件变化时自动刷新。仍有一部分用户习惯把冲突交给自己的 AI 工具处理：他们需要把散落在三方视图里的内容手工整理成一段可粘贴的上下文，容易漏块、漏 base，也容易说错"哪边是 ours"。

Viff 的定位是本地 Git 客户端，不是模型客户端。`internal/ai` 的提交信息生成要求用户在设置里显式配置端点；而冲突解决往往发生在用户已有外部工具（编辑器里的编程助手、网页聊天）的时候。这里要解决的是"把上下文完整、可核对地交给用户"，不是在 Viff 里再放一个模型调用。

## 替代项

- **在冲突查看器里直接调用模型**：需要端点、密钥、失败处理、结果写回与 stale 检查，等于复制 0027 的全部边界，还要承担"模型改错文件"的写回风险。否决。
- **与某个外部工具做集成**：不同工具的协议与能力不同，绑定其中一两家会把维护成本转给 Viff，而用户可能只是想在网页聊天里问一句。否决。
- **继续让用户手工复制三个面板**：能工作，但容易漏 base、漏块，也说不清行号；作为最低成本对照保留。
- **只导出补丁或整文件**：整文件会带上大量与冲突无关的内容，补丁又不含合并后的结果。都不如"按块列 ours/base/theirs 与行号"直接。

## 决定

- 新增纯函数 `app.ConflictContextText`（`internal/app/conflict_context.go`）。输入是冲突查看器已经加载的 `ConflictView` 与 `Operation`，输出一段 Markdown 风格的纯文本；不读文件、不起进程、不联网，可以脱离界面单测。
- 文本包含：仓库根、文件路径、操作类型、ours/theirs 的实际来源标签（来自 `Operation.SideLabels`，拿不到就写 unknown）、冲突类型、行尾与末行换行、块数；每块给出标记顺序（`<<<<<<<` / `|||||||` / `=======` / `>>>>>>>`）、块的行范围，以及 ours/base/theirs 原文（各自带行范围与来源）。
- 指令固定为英文，面向接收方：只改这个文件、删除所有冲突标记、不要暂存/提交、改完回 Viff；单块复制时额外说明其他块不在本文本里。
- 上限：单块 200 行或 20 KB（先到者生效），全文 200 KB。截断处在围栏内写明丢了多少行，全文被截断时写明还有多少块没有包含，绝不静默丢内容。
- 界面在冲突横幅的行动作区放 `Copy for AI`，在按块接受行右侧放 `Copy This Block`。两者只在标记解析可信且至少有一个块时启用，与按块接受使用同一判据；沿用现有 `button` 组件与 palette token，键盘可达，明暗主题一致。
- 只写系统剪贴板，经窗口的 `clipboard` seam 落点（测试替换为记录器，不碰真实剪贴板），随后用现有通知提示"已复制，外部修改后 Viff 会自动刷新"。复制的内容不进日志。
- 不新增依赖、不改设置、不新增网络出口；外部改完文件后沿用现有的文件监听刷新与"标记为已解决"。

## 代价

- 文本里没有冲突块以外的文件内容：外部工具若不能自己打开文件，只能按块返回结果，用户需要自己合并。这是刻意的取舍——避免把整文件塞进剪贴板，也避免把无关内容交给外部工具。
- 200 KB / 20 KB 的截断意味着超大文件只能分块复制、分次处理；截断注说明丢了多少，但不会自动续传。
- 指令与粘贴内容只有英文（接收方是外部 AI）；中文界面下按钮标签走 i18n，粘贴内容仍是英文。
- 多了一段需要长期保持稳定的格式约定：改格式等于改用户的工作流，必须同时改测试与本文档。

## 复审条件

- 用户反复反馈"外部工具只能按块返回"，需要整文件上下文时，重新评估附带块外内容或增加"包含完整文件"选项。
- 出现平台剪贴板容量或编码限制导致复制失败时，重新评估 200 KB 上限与分块方式。
- 若在 Viff 内直接调用模型成为主要诉求（例如用户已配置 0027 的端点并希望一键解决冲突），需要另立 ADR，并先解决写回与 stale 检查。
- 若外部 AI 工具普遍支持直接读取仓库路径（agent 类工具成为主流），可以评估用"打开本地文件"的集成替代大段文本。
