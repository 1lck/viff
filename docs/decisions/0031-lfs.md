# 0031 检测并展示 Git LFS 状态

- 状态：部分被 [0047](0047-lfs-on-demand-statistics.md) 替代（2026-11；自动文件枚举改为按需，其余检测与管理边界保留）

## 背景

使用 Git LFS 的仓库在工作树里看到的往往只是指针文件：看不到真实大小，提交、推送或更新时也可能在 Git hook 或 `git lfs` 缺失处失败。此前 Viff 对 LFS 完全沉默，用户只能从 `.gitattributes`、命令行输出或失败信息里猜仓库是否使用 LFS、本机是否装了 git-lfs。

0.3 的第 4 项要求把「这个仓库是否用 LFS、本机装没装、哪些规则/文件受管、缺依赖怎么办」直接展示出来。Viff 的定位是 Git 客户端而非包管理器，安装系统工具超出它的职责；因此这一项只做检测与展示，不下载、配置或管理 LFS 对象。

## 替代项

- **完全不检测**：改动最小，但用户仍会在提交/推送后才发现缺 git-lfs，错误也指向 hook 而不是缺依赖。
- **集成 LFS 管理**：提供 `git lfs install`、`track`、`pull`、`fetch`、`prune`、对象迁移等入口。它需要理解 LFS 的远端存储、认证与指针文件，并承担「Viff 改了用户全局配置」的责任，明显超出本项范围。
- **直接读 `.git/lfs/objects` 或指针文件**：绕过 Git 与 git-lfs 的版本差异，等于自建一套 LFS 状态来源，容易与真实仓库状态分叉。
- **探测后自动安装**：静默执行包管理器或修改全局 Git 配置既不可移植，也不符合「用户明确决定」的约定。

## 决定

- **能力探测**：`internal/gitcli` 用 `git lfs version` 判断 git-lfs 是否可用，失败是正常状态而不是错误。结果按进程缓存，并以解析后的 Git 可执行文件路径作键，所以设置里换 Git 路径后会重新探测；版本字符串保留在 `LFSStatus.Version` 供诊断与提示使用。探测命令成功但输出为空也算已安装，版本为空。
- **规则解析不依赖 git-lfs**：始终直接读仓库根的 `.gitattributes`；再用 `git ls-files --cached --others --exclude-standard -- ':(glob)**/.gitattributes'` 找到其余属性文件，这样嵌套目录里由 `git lfs track` 写下的规则、以及尚未提交的属性文件也能算进去。每一行按 Git 的字段语义切分（含双引号与转义），只有最终的 `filter=lfs` 才算受管；同一个文件里后面的赋值覆盖前面的（例如 `filter=lfs` 后再写 `-filter` 不算）。嵌套文件的模式加上所属目录前缀，按仓库相对路径展示。每个属性文件上限 1 MiB，模式列表上限 512 条，避免异常仓库拖垮刷新。
- **已安装时的文件列表**：`git lfs ls-files --name-only -z`，路径按 NUL 原样保留；老版本或 shim 只输出换行时按行回退解析。该命令失败不影响规则结果：`Files` 留空，失败保留在 `LFSStatus.Err`（错误仍走 `gitcli` 的分类与错误码），UI 不会把「列不出来」当成「没有 LFS」。
- **返回结构**：`Installed`、`Version`、`Patterns`、`Files`、`Managed`（外加诊断用的 `Err`）。`Managed` 表示仓库使用 LFS：有 `filter=lfs` 规则，或 git-lfs 列出受管文件；两者都没有就是普通仓库。`NeedsInstall` 单独表示「有规则但没装 git-lfs」。
- **应用层**：`RepoState` 增加 LFS 快照。检测与状态查询一样在刷新 goroutine 里执行，结果经 `post` 回到 UI 线程，带 `statusSeq` 丢弃过期结果，不阻塞绘制。检测按「仓库根 `.gitattributes` 的大小 + 修改时间」和 30 秒间隔节流：普通文件系统事件复用快照，`.gitattributes` 变化、元数据刷新（刷新按钮、写操作结束、index/refs 变化）会立即重跑。LFS 检测不是写入，不取写锁，也不塞进 `Workspace.Run`。
- **界面**：仓库使用 LFS 时，状态栏在分支旁显示 `LFS`（能列出文件时是 `LFS 3` 这样的计数），提示里说明规则数/文件数与缺少依赖；有规则但没装 git-lfs 时标记变为警告色。Commit 面板显示紧凑警告条，写明规则数并提供 **Copy Install Command**；仓库打开后每个代次还会弹一次带完整说明的警告通知，动作同样是复制安装命令。安装命令按平台给出：macOS `brew install git-lfs`，Windows `winget install GitHub.GitLFS`，Linux 提示使用发行版包管理器并复制官网地址。Viff 只复制文本，不执行安装，也不运行 `git lfs install`；文案走 `internal/i18n` 的中英文消息表，不新增设置项。
- **隐私与日志**：`repo.refresh` 只增加 `lfs` 小对象：`installed`、`managed`、`patterns`/`files` 计数，以及失败时的稳定错误码。不记录模式、路径、文件名、指针内容或命令输出；没有新增日志事件。检测期间成功读取的 `lfs` 命令不写 Console（失败仍显示），与其它只读刷新一致。

## 代价与边界

- **只检测不管理**：Viff 不会安装 git-lfs、不会执行 `git lfs install`、不会 `track`/`untrack`、不会拉取或推送 LFS 对象，也不修指针文件。缺少依赖时用户仍要自己安装并在终端初始化；Viff 只是把事实和可复制的命令摆出来。
- 负向探测结果按进程缓存：用户在 Viff 运行期间安装 git-lfs，提示要等到重启（或更改 Git 路径）才消失。这是「一次探测、避免每次刷新起进程」的代价。
- 缓存指纹只看仓库根 `.gitattributes`。嵌套属性文件的修改最多等 30 秒或下一次元数据刷新才反映；`.git/info/attributes` 不在扫描范围。已安装时 `git lfs ls-files` 给出的文件列表仍会在每次强制检测时刷新。
- `git lfs ls-files` 报告的是 Git 索引/提交里受管的文件，不是工作树里尚未暂存的 LFS 指针；状态栏数字以此为准。
- Linux 的安装提示只列举常见的包管理器，不检测发行版，也不提供一键安装；复制的文本在 Linux 上是官网地址。
- 属性解析只用于展示，不参与 Viff 的取文件、暂存或提交决策；Git 与 git-lfs 仍是权威。解析覆盖常见的 C 引号与转义，但未实现 Git 属性文件的全部边缘语法（例如属性值里的引号）。模式列表超过 512 条时只保留前 512 条。
- 检测会额外启动 `git lfs version`/`git lfs ls-files`/`git ls-files`，首次打开仓库比之前多一次轻量查询；节流把它限制在 refresh 的少数几次而不是每次文件事件。

## 复审条件

- 用户明确要求在 Viff 内安装/初始化/跟踪 LFS，或希望直接查看、下载 LFS 对象时，另立 ADR 评估管理面与凭据边界，不把安装逻辑塞进本文的实现。
- 运行中安装 git-lfs 后的过期提示成为常见反馈，或 git-lfs 提供无需重启即可刷新能力状态的稳定接口时，改为可失效的探测缓存。
- 大型仓库里属性扫描或 `git lfs ls-files` 成为刷新瓶颈（有可复现的耗时数据）时，改为按需检测、增量缓存或后台预取。
- `.git/info/attributes` 或嵌套属性文件的实际使用比例明显上升，需要纳入指纹或实时检测时，重新评估缓存键与代价。
- Git LFS 上游改变 `ls-files` 的机器输出或指针规范，或 Viff 决定捆绑 git-lfs 时，重新评估探测与版本判断。

## 验证

`internal/gitcli` 用表驱动测试覆盖 `filter=lfs` 规则解析（注释、引号、转义、嵌套目录、重复/覆盖、CRLF、制表符）与文件列表解析（NUL 与换行回退、保留空格）；能力探测、已安装与文件列表失败路径通过 `Runner.LFSCommand` 注入 seam 测试，不依赖本机是否安装 git-lfs，也不访问网络。`internal/app` 覆盖刷新后的 LFS 快照、`.gitattributes` 变化触发的重新检测、30 秒节流与元数据刷新强制重查，以及日志字段只有计数/状态/错误码。`internal/ui` 的 `vivahead` 用例断言状态栏标识、Commit 警告条、通知与复制动作出现，并检查空闲无重绘循环。测试中的所有 Git 仓库都是 `t.TempDir()` 里的临时仓库。
