# 0035 在文件中查找：按需内容搜索

- 状态：已采用（2026-11）

## 背景

0024 的 Quick Open 只能按路径过滤工作树里已有的文件：用户能定位“文件在哪”，却回答不了“这段文字在哪些文件里”。IntelliJ 的 Find in Files 是这类动作的参照——输入一段文本，列出路径、行号与行内容，回车打开。Git 自带 `git grep`，但 Viff 需要先决定几件事：是否建索引、默认依赖哪个后端、结果如何限制，以及怎么和 0024 的“不做全项目搜索”边界衔接。

约束来自项目定位：不构建 IDE、不常驻后台索引、不把工作树复制成第二份事实来源。Git 是仓库事实来源，内容搜索每次都应读到当前工作树。

## 替代项

- **集成 Everything**：Everything 只索引文件元数据，不索引文件内容；[官方说明](https://www.voidtools.com/support/everything/searching/)明确写 “Because file content is not indexed, content searches can be extremely slow”。它只在 Windows 可用，要求用户已安装并运行，返回路径而不是行号，也不遵守 `.gitignore`。要在 Viff 里补齐仓库范围、忽略规则和行级结果，等于自己再写一层内容搜索。否决。另外，0032 已经否决“与某个具体外部工具做集成”：不同工具的能力与协议不同，绑定其中一两家会把维护成本转给 Viff。
- **自建常驻索引（倒排表或后台扫描落盘）**：查询会快，但要在磁盘写缓存、处理失效（外部 AI、编辑器、终端都可能改工作树）、限制内存与首次索引时间；大仓库首次建索引本身可能比一次查询更慢。这与“不设常驻后端服务、缓存只加速不替代 Git”冲突。否决。
- **只做当前文件内搜索**：Diff 与文件查看器已有 ⌘F，解决的是“在这个文件里找”，不解决“在哪里用了这个字符串”。否决。
- **外部工具钩子（把查询转给用户配置的命令或 IDE）**：没有统一的结果列表、行号跳转与取消语义，还要再维护一套外部工具配置；结果也无法和 Viff 的只读查看器对齐。否决。
- **Quick Open 保持单页签，路径与内容混在一个结果列表**：两种匹配语义、两种空状态和两种排序混在一起，键盘选择会变得不可预测。改为两个页签。

## 决定

- Quick Open 改成 **Search** 对话框，两个页签：**Files** 与 **Contents**。Files 保持 0024 的路径子串过滤；Contents 按文件内容搜索工作树。
- 快捷键：**⇧⌘F（Windows/Linux 为 Ctrl+Shift+F）** 直接打开 Contents；**⇧⌘O** 仍打开 Files。对话框打开后可在两个页签之间切换。
- **不建索引、不落盘**：每次查询直接读工作树。默认后端是 `auto`：已安装 ripgrep 时优先用它，否则用 `git grep`；也可以在设置里显式选择 `git` 或 `rg`。`git grep` 走 `-n -z -I -F`，包含未跟踪文件并遵守 `.gitignore`。ripgrep 不随应用打包，需用户自行安装；设置里可填路径，留空从 `PATH` 查找；未安装或选择 `rg` 但找不到时回退 Git grep，并提示下载地址 <https://github.com/BurntSushi/ripgrep/releases>。
- 范围遵守 Git：索引文件加未跟踪文件，排除 ignored；跳过二进制文件（`git grep -I`）；ripgrep 还跳过大于 2 MB 的文件（`--max-filesize 2M`）；不进入子模块内部。
- 查询是**字面量**匹配（`-F`）。第一版不提供正则、整词、大小写与路径过滤。
- 输入去抖；新查询、切换仓库或关闭对话框会取消上一次查询，迟到的结果丢弃。单次最多返回 **300** 条命中，达到上限时提示“只显示前 300 个匹配，请缩小搜索范围”。
- 结果显示相对路径、行号与该行文本；回车以只读方式打开命中文件，Esc 关闭。查询文本不写入事件日志。
- **双击 Shift 未采用**：Viva 目前只在终端 raw 模式下投递修饰键，普通窗口收不到单独的 Shift 按下事件。这是上游能力缺失，待 Viva 支持后复审；当前不排期，也不把它写成已计划。
- 与 0024 的关系：0024 中“明确不做 … 全项目搜索”的其余边界（编辑、补全、跳转定义、引用、符号大纲）不变，只有“全项目搜索”一条由本 ADR 的按需内容搜索部分取代。

## 代价

- 大仓库每次全量扫描。一次开发机实测（冷页缓存未命中，未记录平台与 Git 版本，只作数量级参考）：vscode 仓库 20,562 个跟踪文件约 29 秒，Viff 自身 765 个文件约 68 ms。因此必须有去抖、取消与 300 条上限；用户仍可能等几秒到几十秒。
- 没有索引就没有“秒出”的体验，也无法搜索 ignored 文件、跨仓库或历史提交；要搜这些内容需要另一次查询或另一个工具约定。
- 第一版只有字面量匹配：不能写 `\bFoo\b`、不能忽略大小写、不能限定 `*.go`。用户需要这些时只能回到外部工具。
- 300 条上限会隐藏后面的命中；结果按 Git/ripgrep 的输出顺序返回，不额外排序，用户需要缩小关键字才能看到其余结果。
- ripgrep 可选带来环境差异：未安装时用 Git grep，速度与文件边界（二进制、2 MB、隐藏文件）可能不同；两套后端要分别维护参数与解析，测试也要覆盖回退。
- 需要维护 `git grep -z` 与 ripgrep JSON 两套机器格式解析。两者都不是 Viff 定义的格式，升级时要做兼容验证。

## 复审条件

- 用户需要正则、整词、大小写或路径过滤时，扩展查询选项，而不是让用户改用外部工具。
- 大仓库一次查询的等待不可接受（例如常见仓库普遍超过 5 秒），或再次出现无法取消的查询：先量一次扫描时间，再评估增量索引、目录级并发或更激进的上限。
- Viva 支持普通窗口的修饰键事件后，评估“双击 Shift 打开搜索”是否仍值得引入；在此之前不排期。
- 需要搜索 ignored 文件、子模块内部或跨仓库时，重新设计范围与缓存策略，不把当前实现悄悄扩成第二套索引。
- ripgrep 成为大多数用户的实际默认，或打包诉求超过体积预算时，重新评估是否随应用分发及其许可证、升级责任。
