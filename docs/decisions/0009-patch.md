# 0009 补丁的创建与应用

- 状态：已采用（2026-11）

## 背景
改动需要在两个 checkout、两台机器或评审者之间搬运时，最轻的载体是 Git 自己的补丁格式：`git diff` 写出，`git apply` 应用，不经过远端。设计稿没有把它列成独立模块，但它属于“工作区与提交”的日常动作。

## 决定
- 创建用 `git diff`，不自己序列化改动。`--binary` 让二进制文件的改动也能往返；`--no-color`、`--no-ext-diff`、`--no-textconv` 保证输出是给 `git apply` 的原文而不是给人看的渲染结果。
- 强制 `--src-prefix=a/ --dst-prefix=b/` 和 `--no-relative`，抵消用户 `diff.noprefix`、`diff.mnemonicPrefix`、`diff.relative` 对前缀和路径的改写；否则补丁换一个仓库就无法应用。
- 一次补丁只覆盖一个区域：暂存的改动比较索引与 HEAD，未暂存的改动比较工作树与索引。选择同时落在两个区域时菜单项不可用，不做隐式合并。
- 重命名的条目要把旧路径和新路径一起传给 `git diff`，否则 Git 会把重命名写成“新文件”，应用后会多出一份副本。
- 应用先用 `git apply --check` 校验整份补丁，通过后再应用；失败时不写入任何文件，界面原样展示 Git 的错误。应用到索引（`--cached`）只改 index，工作树保持不变。

## 代价
- 未跟踪文件没有可比较的对象，不会进入补丁；冲突文件也不能写成补丁。这两种情况需要用户先暂存或先解决冲突。
- 补丁依赖上下文行匹配，目标仓库的同一文件改动较多时可能无法应用。

## 复审条件
需要把未跟踪文件也带上时（先 `git add -N` 再 diff），或需要一次生成跨区域的多个补丁时，再扩展这次的决定。
