# 0034 可自定义的提交信息规则

- 状态：已采用（2026-11）

## 背景

[0027](0027-ai-commit-message.md) 把「写提交信息」交给模型时，规则是写死的：`internal/ai` 里一段 Conventional Commits 的说明，加上一句语言指令。这对多数仓库够用，但团队对提交信息的格式要求并不统一——有的要求 Jira 前缀（`VIFF-123 feat(ui): …`），有的用 `[模块] 描述`，有的根本不用 Conventional Commits。

规则写死意味着这些团队只能放弃这个功能，或者每次生成后手工改一遍。

## 替代项

- **不给自定义**：把功能留给接受 Conventional Commits 的仓库。代价是格式不同的团队用不上，而这正是最初提出需求的原因。
- **切成四个槽位**（instruction / format / constraints / output）：用户只能填空。但 `[模块] 描述` 这类结构与槽位的固定骨架冲突，且分隔符与拼接顺序会变成文件格式的一部分，以后每改一次结构就要迁移一次。
- **连上下文一起开放**（用占位符重排 branch/recent/files/diff）：能把提示词完全变成模板，但用户消息同时承载 Git 上下文与隐私边界（4000 字符、8 文件、跳过 lock），开放它会让截断责任从程序转到用户，出问题时无法判断是模板还是模型的错。
- **每仓库一套规则定义**：规则文本按仓库存进仓库自己的元数据。代价是一个团队要在每个仓库复制同一套规则，改一次要改 N 处。

## 决定

- **开放范围只有一处**：模型收到的 system 指令（「规则」）。用户消息的五段（分支、最近提交、变更文件、diff、重跑要求）仍由程序拼装，不开放为模板；留出 `{{branch}}` 类占位符的做法留待以后需要时再评估。
- **自定义规则时上下文必须中立**：内置规则的分支保持逐字节不变；用户规则生效时，最近提交改标为「for naming reference only — do not copy their format」，重跑要求改用「different wording and structure」，不再出现 `type`/`scope`，system 指令在规则正文后追加「规则优先于上下文中的任何示例，不要模仿最近提交或上一条消息的格式」。最近提交照常发送，只是从「格式示例」降为「命名参考」。否则一句「一句话输出，禁止任何前缀」会输给上下文里现成的 `feat(ai): …` 示例。
- **规则是命名的文本集合**：每条规则有名称与正文。内置规则随程序发布，是虚拟的——永远排第一、永远不能被编辑或删除，因此任何时候都有一个已知可用的退路。
- **选中状态按项目，并回退到上一次的选择**：`prompts.json` 里 `repositories` 记录「规范根路径 → 规则 ID」，另有 `lastRule` 记录最近一次选中的规则。解析顺序是**仓库自己的记录 → `lastRule` → 内置规则**。规则定义本身全局共享，一个团队写一套、各仓库按需选用。任何一步指向的规则已被删除，都继续往下一级回落。
  - 加 `lastRule` 这一步是因为只按仓库记会违背直觉：用户在 A 项目选了规则，打开从没设置过的 B 项目就悄悄变回内置规则，看起来像「选中没有生效」。现在没设置过的仓库继承上一次的选择，用户一旦手动切换就以该仓库的记录为准。
  - 选「使用内置规则」时同时清空该仓库的记录和 `lastRule`，否则下一个仓库会把用户刚放弃的自定义规则当成默认。

- **文件位置与格式**沿用 [0020](0020-repositories-changelists.md) 的 ChangeList 范式：`prompts.json` 与 `settings.json` 同目录、原子写（临时文件 + `Sync` + `Rename`）、版本高于本程序时只读且不覆盖、损坏文件报错但不被替换、加载时在内存里修复不一致（空名称、空正文、重复 ID、悬空引用）。内置规则从不写入该文件，所以「没有记录」就是「用内置规则」，旧文件与旧版本因此照旧可用。
- **交互入口是 AI 按钮的右键**：左键仍然是「生成」，右键打开规则菜单（选择、新建、编辑、重命名、删除、使用内置规则）。这样提交面板的 Amend 行布局不变，不必为了一个选择器挤压已经只有 240px 的最窄宽度。
- **生成前默认二次确认**：`aiConfirmGenerate` 默认为 true，点击 AI 按钮先弹一个确认框，写明「把当前改动发送到已配置端点」。开关本身放在同一个右键菜单里——它描述的是这颗按钮的行为，想关掉它的人正好在看这个菜单。关闭后恢复原来的「点一下直接生成」。默认开启的理由是这一步会把 diff 发到外部端点，属于 [0027](0027-ai-commit-message.md) 已确立的隐私边界，不该因为多加了一层菜单而被悄悄弱化。
- **语言指令由程序追加，且区分两套措辞**：内置规则生效时沿用原文（点名 Conventional Commits 的 token），自定义规则生效时改用格式中立的说法（保留「上文规则定义的」英文 token）。若对自定义规则也点名 Conventional Commits，用户选的 `[模块] 描述` 会与语言指令互相矛盾，模型输出不可预测。
- **不做校验，只做提示**：模型回答原样填入提交框，Viff 不解析结构。要求 JSON 之类的结构化输出是用户的选择，编辑框用一行说明写清这一点；空回答仍然报错，不会被静默当成「模型没话说」。

## 后果

- 内置规则的输出与改动前逐字节一致：默认路径沿用原来的语言指令，`Rules` 为空即回到内置文本。已有用户感知不到任何变化。
- 自定义规则文本与请求一起发送到用户配置的端点，隐私边界因此扩大了一句：发送内容现在还包括用户自己写的规则。`docs/privacy.md` 已同步。
- 用户可能写出让模型输出非提交信息的规则（例如要求 JSON 或解释性段落），结果会原样进入提交框。这是规则作者的责任，程序只保证不解析、不静默改写、空结果报错。
- 自定义规则不再被上下文里的内置格式示例抵消：用户写「一句话、不要前缀」时，最近提交中的 `feat(scope): …` 不会被模型当成格式要求。代价是自定义规则下的用户消息比内置路径多出这些中性措辞，且最近提交的「参考」语义依赖模型理解那句英文提示。
- 规则文件与设置分开，随设置一起被复制或备份时也会一起走；密钥仍只在 `settings.json`。
- 悬空引用由 `storage.normalize` 清理，因此删除一条正在被某仓库使用的规则不会留下半个坏状态，该仓库下次读取即回到内置规则。

## 复审条件

- 若出现「同一仓库需要按分支/变更类型选不同规则」的明确需求，重新评估选择键（现在只按仓库根）。
- 若两个 Viff 实例同时开着同一份 `prompts.json` 成为常见用法，评估让规则列表在打开菜单时重读文件：现在读路径只在首次加载时读盘，写路径才重读，所以 A 窗口保存的规则要等 B 窗口下一次写入或重启才可见。
- 若用户普遍要求重排上下文（例如只要文件列表不要 diff），再评估把用户消息模板化，并在那时一并决定截断与隐私边界如何继续由程序守住。
- 若规则数量增长到需要分组、导入导出或团队共享文件，评估把规则定义移出 `prompts.json` 单文件（可能需要独立的库文件格式与 ADR）。
- 若模型侧开始支持结构化输出（JSON Schema 等），评估在填入提交框前解析并校验，而不是继续原样写入。
- 若上下文中性化后模型仍稳定模仿最近提交的格式，重新评估自定义规则下是否发送最近提交，或把这段上下文改成可配置项；届时一并决定隐私边界与提示词责任的归属。
