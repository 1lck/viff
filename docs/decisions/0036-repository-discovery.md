# 0036 从父目录发现并批量导入仓库

- 状态：已采用（2026-11）

## 背景

Windows 用户经常把多个项目放在同一个工作区目录里，例如 `workspace/project-a`、`workspace/project-b`。选择这个父目录打开时，Git 的 `rev-parse --show-toplevel` 会失败，界面只显示 `not a git repository (or any of the parent directories): .git`，用户无法从列表里发现子目录中的仓库。

[0020](0020-repositories-changelists.md) 明确选择“工作区保存用户显式添加的仓库，不自动扫描目录”。父目录导入不能推翻这条约束：启动时扫描磁盘、或在打开任意目录时静默导入，都会让工作区内容不可预期，也会把大目录的遍历成本带进打开流程。另外，一个仓库内部还可能嵌套独立仓库、submodule 或 linked worktree；只扫描一层会漏掉这些同样是独立工作树的对象。

## 替代项

- **启动时或打开目录时自动扫描并自动导入。** 违反 0020 的可预期性，且用户无法拒绝一次大目录遍历，不采用。
- **只放宽目录选择器，让 Git 在父目录执行。** Git 没有“列出子仓库”的原语；放宽选择器只会把原始错误换成另一种错误，不采用。
- **只检查目录名或 `.git` 是否存在就当成仓库。** 目录名不构成证据，损坏的 `.git` 或普通空目录会被误报；Git 才是仓库事实来源，不采用。
- **只扫描所选目录的一层子目录。** 会漏掉嵌套仓库、submodule 与 linked worktree，不采用。
- **无深度、无数量上限地递归。** 会把 `node_modules`、构建产物等无关目录全部走一遍，用户无法取消，不采用。
- **在父目录执行 `git init` 或把多个仓库合并成一个。** 改变用户磁盘且破坏“一个仓库一次写操作”的边界，不采用。

## 决定

- 只在用户显式触发时扫描：打开一个不是仓库的目录时提供“发现仓库”对话框，或在 Repositories 总览选择 **Find Repositories…** 对任意目录扫描。扫描结果不会自动改变工作区，必须勾选后导入。
- 扫描在 `app` 层后台任务中执行（`internal/app/discovery.go`），可取消；关闭对话框会取消任务。默认最大深度 4、最多遍历 2000 个目录、最多返回 200 个仓库，超过上限返回“已截断”状态而不是失败。
- 不跟随符号链接，避免循环；跳过 `.git` 与 `node_modules`、`vendor`、`target`、`dist`、`build`、`bin`、`obj` 等依赖/产物目录。
- 只有包含 `.git`（目录或文件）的目录才进入候选，再对每个候选运行现有 `Discover` 由 Git 确认；只有返回的工作树根等于候选目录本身时才接受，避免损坏的 `.git` 让 Git 回答外层仓库。
- 发现仓库后继续进入它的子目录，因此普通嵌套仓库、submodule（`.git` 文件）和 linked worktree（`.git` 文件）都会作为独立条目列出；按解析符号链接后的工作树根去重，父子仓库互不合并。
- 导入时对每个根重新执行 `Discover`，再由工作区去重后加入列表；导入不切换活动仓库，完成后打开 Repositories 总览供用户检查。
- 父子仓库同时导入后，父仓库把子仓库目录显示为嵌套仓库/gitlink 变化，这是 Git 自身语义；Viff 不提供跨仓库提交。

## 代价

- 按名称跳过依赖/构建目录会漏掉刻意放在其中的仓库；深度与数量上限也会漏掉更深的仓库。两者都在对话框里以截断提示暴露，用户可以缩小范围后重扫。
- 每个候选目录都要启动一次 Git 探测，扫描成本与候选数量线性相关；目录预算限制了这个成本的上界。
- 不含 `.git` 的 bare 仓库没有工作树，不会被列出；子模块需要先有可读取的父仓库元数据，父仓库损坏时子模块也将无法导入。
- 发现结果只是快照；导入前会重新查询 Git，但两次查询之间仓库仍可能变化，此时按失败处理而不是猜测。

## 复审条件

- 用户报告工作区内实际的仓库被漏掉（被跳过目录、深度或数量上限挡住），需要把上限或跳过名单做成设置项。
- 扫描在常见工作区目录上耗时明显（以真实目录和 `startTask` 事件测量），需要改为增量返回或调整默认值。
- 0020 的工作区模型变化（例如引入自动监视或跨仓库操作），需要重新评估“显式导入”的边界。
